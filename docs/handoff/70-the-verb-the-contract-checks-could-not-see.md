# §70. The verb the contract checks could not see — a hard-coded list of another module's exports, inside the family of checks written to end exactly that

**Date:** 2026-08-02 · **Migration:** none · **Backend:** unchanged · **Frontend:** +16 tests, all generated
**Browser pass:** none owed — see below. **Queue rows added:** frontend (one, recording that none is owed).

## How it was found — the loose end §69 left, followed

§69's build-status note recorded a discrepancy and deliberately did not chase it:

> the previously recorded total was 506 and the run now reports 518, so **four tests came from
> somewhere this slice did not count** — noted rather than reconciled, and worth one grep next
> session, since a test appearing without an author is the same class of thing as a test
> disappearing.

The grep was worth it. The four tests are real, they have an author, and finding the author found a
defect that had been live for eight slices.

`contractOperations.test.ts`, `apiResponseTypes.test.ts` and `contractParameters.test.ts` are
**data-driven**: each discovers `api.*` call sites through the TypeScript compiler and emits one
`it.each` case per site. So a slice that adds an endpoint adds tests it did not write — the four
were generated by §69's own three new call sites, and the arithmetic is *not* 3 + 3.

It is 2 + 2, and the missing third is the finding.

## The defect: `api.delete` does not exist and never has

Both checks carried their own copy of the client's verb list:

```ts
/** The HTTP verbs `api` exposes, as spelled on the client. */
const API_METHODS = new Set(['get', 'post', 'patch', 'put', 'delete']);
```

The client does not spell them that way. `api/client.ts` exports `del` — not `delete` — and an
`upload` that is not in the list at all. `grep -rn "api\.delete" src/` returns **nothing**: the
string `'delete'` in both files matched no call site on the day it was written and none since.

The consequence is eight call sites invisible to **both** checks:

| Call site | Never asked |
|---|---|
| `cases.ts`, `suites.ts`, `admin.ts` ×2, `documentation.ts`, `runs.ts`, `projects.ts` (§69) — `api.del` | whether the SPA's `DELETE` resolves to an operation the contract declares |
| `runs.ts` — `api.upload` (§67, evidence) | whether its response type is generated rather than written by hand |

Every delete in the product, and the one upload. §53's own header says an undeclared operation is
invisible to every check that starts from the spec and that *"you have to start from the caller"* —
and the check that starts from the caller could not see a fifth of the callers.

## Nothing could catch it, and the reason is the interesting part

Both files are written by an author who had already been burned by vacuity, and both carry guards
against it:

- `callSites.length >= 40` — met comfortably by the four verbs that *did* match;
- `typeArguments.length >= 25` — likewise;
- **distinct verbs `>= 3`** — the closest miss. It was written to catch precisely "this check has
  stopped discriminating by method", and four verbs sail past a threshold of three.

A guard by **count** cannot see a systematically absent category. It answers *"is this check still
running?"*, and the check was running perfectly — over a client one verb smaller than the one that
ships. This is §48's rule (*a catalogue-wide invariant needs a computed check, not a careful
reading*) arriving **inside the §48 family of checks**, which is what makes it worth a section: the
four contract-hygiene checks were the project's answer to hand-maintained agreement, and one of them
hand-maintained a copy of `client.ts`'s export names.

The comment is the tell, and it is worth keeping in mind as a smell in its own right: *"as spelled
on the client"* is a claim about another module, written in this one, that nothing checks. §58's E1
is the same shape (a third copy of the privilege-split SQL under the instruction *"keep the two in
step"*, already drifted), and there the fix was also to **delete the copy** rather than correct it.

## The fix: derive the verb set from the client

`contractIntrospection.apiMethods` reads `client.ts` through the TypeScript program that was already
being built, and maps each member of the exported `api` object to the HTTP method it actually
sends — taken from the `RequestInit` handed to `request`, with "no `method` key" meaning GET, which
is exactly how `api.get` is written.

**The mapping matters as much as the membership.** `contractOperations` asks whether a path item
declares this method, and path items are keyed by the *OpenAPI* spelling — so `del` must arrive as
`delete` and `upload` as `post`. Teaching the check the client's names alone would have replaced
"unchecked" with "compared against a method no path item can ever declare", which is a red test for
a wrong reason and would have been read as a false positive.

`apiResponseTypes.test.ts` also built its **own second `ts.createProgram`** over the same sources —
predating the shared module — and now uses `contractIntrospection`'s. One program, one verb set, one
definition of what a call site is.

### The guard the count could not be

`unresolvedApiVerbs` is the other half. A member of the `api` object whose method cannot be read is
**recorded and exported**, and both checks assert the list is empty. A verb written in an unfamiliar
shape is now a failure rather than a silently narrower check — being dropped is exactly how `del`
and `upload` went eight slices unexamined.

## What the newly-covered call sites said: nothing

All sixteen generated cases pass. There was no second defect hiding behind the first — every
`api.del` resolves to a declared `delete` operation, and the upload to a declared `post`.

That is worth stating plainly rather than glossing: the blind spot was real and open for eight
slices, and this time it happened to be empty. It is evidence about the contract's health, not
evidence that the check did not matter — the same reasoning §61 used for its no-defect live pass.

## Mutations — both run inline

This slice's whole content is a check, so the mutations are the only way it can be verified at all;
they were run rather than queued.

| Mutation | Result |
|---|---|
| Leave the client spelling unmapped (`del` compared as `del`) | **exactly 8 red** — the 7 deletes and the upload, and nothing else. The check discriminates by method on precisely the sites it could not see before. |
| Make `httpMethodOf` unable to read one verb (return `undefined` for `DELETE`) | **exactly 2 red**, one per file — *both* vacuity guards, which is the property that did not exist before. The old code's response to the same situation was silence. |

## Defect class swept, not the instance

The rule this violates is "a list mirroring another module's exported names, maintained by hand".
The siblings were checked rather than assumed:

- `OPERATION_KEYS` (both frontend and backend) lists **OpenAPI path-item keys**, which is a property
  of the spec format, not of another module — correct as written, left alone;
- `ContractParameterBindingTest` reads the live `RequestMappingHandlerMapping` out of the Spring
  context, so it derives the controller surface rather than restating it;
- `OpenApiContract` parses the YAML as written, for the reason its own javadoc gives.

So the class has exactly the two instances fixed here.

## Left for later, deliberately

- The carry-overs stand: the artifact register's plan filter is still `useState` rather than the URL
