## The five things worth carrying

### 1. `adoptSession`, not a second writer of the token

`AuthProvider.login` is the only writer of `tcms.token`, and it also writes the user cache, sets
`status`, and publishes on the cross-tab channel. A callback page calling `safeStorage.set` directly
would leave `user` null, `status` stale and sibling tabs uncorrected — **a signed-in app rendering a
signed-out shell.** So one seam was added beside `login`, doing the same four things. `TOKEN_KEY` is
still not exported.

**The user is not in the fragment**, so `adoptSession` round-trips `/me` before it can claim
anything — which is the mechanism `AuthProvider` already documents as correct: *restoring a session
is a server question.* A rejected `/me` **clears the token**, and the asymmetry with the mount-time
confirmation is deliberate: there, a 500 must not sign everybody out over a backend restart, because
the session is one the user already had. Here there is nothing to preserve.

### 2. The fragment is read during the first render, not in the effect

The effect wipes it — a live session in the address bar survives a copy-paste, a screen share and
the browser's own history. React runs effects **twice** under StrictMode, so an effect that read
*and* wiped would see an empty hash the second time and **report a failure for a sign-in that
worked.** Captured in a `useRef` initialiser, wiped in the effect, adoption guarded by a second ref.
Same class of defect as `AuthContext`'s `ignore` flag.

### 3. `expiresAt` is parsed and ignored, and the file says why

It is in the fragment because `AuthResult` carries it and both sign-in paths mint the same session.
**Nothing in this SPA has ever stored a session expiry.** The server enforces it (8h/30d, plus the
`pv` epoch); a client-side copy is a second notion of when a session ends that nothing enforces and
that drifts on any clock skew.

### 4. Discovery is silent about its own emptiness — and four of the six sign-in tests assert an absence

`POST /auth/providers` answers **200 with an empty list** for an unclaimed domain, a disabled
provider and a malformed address alike, because a login surface must not be an oracle for which
companies exist here (§6r). So the buttons appear when the list is non-empty and **nothing at all**
appears otherwise — no message, no empty state, no spinner resolving into a shrug. **A failed
discovery renders identically**, which is why that test needs `drivingAFailedWrite()`: the failure
*is* the subject.

The standing caption — *"Local account. Single sign-on arrives with the integrations release."* —
went with the block that replaced it. It had been false since §217 shipped.

Discovery is a **mutation for a read**: the operation is a `POST` because an email address in a query
string lands in access logs, browser history and `Referer` headers, and this one is typed by somebody
who has not signed in and may never do so. It fires on **blur**, not per keystroke.

### 5. `authorize` is a navigation, not a fetch

`GET /auth/sso/{providerId}/authorize` answers **302 to a third-party origin**. A `fetch` would
follow it into a CORS failure at the issuer, and the point is to put the *browser* at the issuer's
login page. `window.location.assign` against the API origin — which is why `BASE` is now exported
from `api/client.ts` rather than spelled again in a component.

## Where the plan was wrong, and what the code said instead

Every one of these was found by reading the file the plan described.

- **`clientSecret` cannot be omitted.** The plan's dialog test asserted the payload has *no*
  `clientSecret` property when the field is blank — copying `NotificationChannelDialog`, where
  absence is the keep. But `IdentityProviderInput` lists `clientSecret` on its **`required`** array,
  so an omission is a body the contract refuses and §199's request-payload check would fail it. The
  contract's own description says **null keeps the stored secret**. So the keep is a present `null`
  here and an absent key there, and the two dialogs' headers now each say which and why. Five of
  that schema's properties are required-and-nullable, so the payload always carries all ten.
- **`keys.emailDomains` cannot be `['identity-providers', 'email-domains']`.** TanStack matches an
  invalidation by prefix, so the plan's key — which mirrors the URL — would be swept away by every
  `invalidateQueries(keys.identityProviders)`, contradicting the same comment's claim that the two
  are edited apart. It is `['identity-provider-email-domains']`.
- **`NotificationSettingsPage` is in `features/settings/`, not `features/admin/`.** The plan's file
  structure implied otherwise. It is still the precedent for the ungated rail entry.
- **Neither dialog precedent uses React Hook Form.** The plan specified RHF + Zod *"matching
  `IssueTokenDialog`'s shape"*; `IssueTokenDialog` and `NotificationChannelDialog` both use plain
  `useState` with a `fieldErrors` record and `describeError` for the form-level alert.
  `ProviderFormDialog` follows the code, not the plan. LoginPage keeps its RHF form.
- **The provider button's test id carries no uuid.** The plan wanted
  `Login.Provider.${provider.id}`; `test-ids` rule 6 says a locator built from a uuid is
  unaddressable. It is `Login.Provider`, addressed by index.
- **`LoginPage.test.tsx` and `AuthContext.test.tsx` did not exist.** The plan said "modify".

## The https gate is checked on the client too, and that duplication is deliberate

`ProviderFormDialog` refuses a non-`https://` issuer before the server has to. The server refuses it
anyway (§219 decided that gate **stays**), but a 400 field error cannot carry the reason: the issuer
URL is where the signing keys are fetched from, so over plain HTTP whoever is on the path chooses who
may sign in. Checked client-side so the message can say that.
