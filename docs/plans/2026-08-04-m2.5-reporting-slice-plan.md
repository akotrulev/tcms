## 2. Current state — what reporting can build on, and what is genuinely absent

### 2.1 The `reporting` module does not exist

`CLAUDE.md`, the ERD §0.2 and `be-java.md` all list `reporting` among the modules. **There is no
`backend/src/main/java/com/tcms/reporting/` directory.** `ModuleStructureTest.detectedModulesMatchTheSourceTree`
hard-codes the nine that do exist (`auth · documentation · execution · identity · project ·
provisioning · repository · tenancy · work`) and its `@DisplayName` rationale says in as many words
that adding one *"is expected as the plan's remaining modules land (reporting, shared) — but it must
be a deliberate edit, so that whoever adds one also reads the `allowedDependencies` rule they are now
subject to."*

So creating the module is a two-file act plus a test edit, and it is the first slice's first task.
`shared` does not exist either and this plan does not create it (§3, decision E).

`repository.DashboardController`'s own header already records why the dashboard did **not** wait for
this module: *"a `reporting` module would mean that module reading this one's tables — the
cross-module edge ArchUnit refuses — to compute numbers this module already knows how to count."*
That reasoning is correct and this plan does not overturn it: the dashboard stays in `repository`.

### 2.2 The tables are all already there

`V1` created the entire reporting section — `execution_fact`, `suite_run_summary`, `plan_snapshot`,
`case_health`, `report_definition`, `report_artifact` — all six on `V1`'s `company_owned` RLS array,
all six carrying `company_id NOT NULL`, all six with the `V4` `nullif(…, '')` predicate applied by
that migration's rewrite. `execution_fact` has five purpose-built indexes
(`(company_id, case_id, executed_at DESC)`, `(company_id, plan_id, executed_at DESC)`,
`(company_id, release_sort_key)`, GIST on `suite_path`, GIN on `feature_ids`) which have been
maintained on an empty table since M0.

**Four of the six are completely dead** (`execution_fact`, `suite_run_summary`, `plan_snapshot`,
`report_definition`, `report_artifact` — five, in fact; only `case_health` has any code).

> **Naming trap, live today.** `com.tcms.execution.PlanSnapshot` is §74's *plan-version snapshot value
> object* and has nothing to do with the `plan_snapshot` **table** in the reporting section. Two
> unrelated things with one name, in a codebase where the reporting one has no code yet. Any slice
> that gives the table a writer must not put it in a class called `PlanSnapshot`.

### 2.3 Every `execution_fact` column has a source — checked column by column

| `execution_fact` column | Source |
|---|---|
| `execution_id` (PK), `company_id`, `project_id`, `case_id`, `case_version_id`, `release_version`, `release_sort_key`, `executed_by`, `executed_at`, `duration_ms` | `test_execution` — all present, `release_*` already denormalized there by `V1` |
| `run_id`, `plan_id`, `configuration_id`, `source` | `test_run` (`configuration_id` is `NOT NULL` there, which is what makes the fact column's `NOT NULL` satisfiable) |
| `suite_id`, `suite_path` | `test_case` → `suite.path` (`ltree`) |
| `status_kind`, `counts_as_pass` | `case_status.kind` / `.counts_as_pass`. `V1`'s own comment on `kind`: *"Lets reporting aggregate project-custom statuses without knowing their names."* |
| `automation_status` | `test_case.automation_status` |
| `test_type_id`, `test_level_id`, `feature_ids UUID[]` | `case_classification` → `classification_dimension` |

**The derived constraint that shapes everything downstream:** `execution_fact.status_kind` is
`NOT NULL` and `test_execution.status_id` is nullable, so **the fact log can only hold *recorded*
executions**. That is the same rule `ExecutionFacts` already states for the health recompute —
*"recorded means `status_id IS NOT NULL`… not 'an execution row exists'"* — and it means
`notRun`/coverage denominators can **never** come from `execution_fact`. §6e's headline totals need
the plan's scope as the denominator, exactly as §46 found for plan statistics.

### 2.4 The seam precedent is well established, and this would be the fifth instance

`repository` may not depend on `execution` and vice versa; ArchUnit enforces it. Four classes already
concentrate one module's crossing into one file:

- `execution.CaseFacts` — `execution` reading `repository` tables (11 crossings as of §82)
- `repository.ExecutionFacts` — `repository` reading (and `INSERT … SELECT`-ing into) `execution`'s
- `work.BoardFacts` — `work` reading both, and the §81/§84 precedent for *concentrating a
  cross-module read where no other module may write the query*
- `documentation.PlanFacts` — `documentation` reading `execution.test_plan`

`reporting` needs the fifth. Its query names `test_execution`, `test_run`, `test_case`, `suite`,
`case_status` and `case_classification` — three modules — and **no existing module may write it**:
`repository` may not see `test_run`, `execution` may not see `suite`, and `work` is the board's
module and has no business filing a report. §81's argument (*"the module that already concentrates
every foreign-table statement in one file"*) applied to a module that does not exist yet gives the
same answer from the other end: create it, and give it one seam file.

**Crucially, `ExecutionFacts` already proves the exact statement shape this needs is safe under RLS**:
its `INSERT … SELECT` into `case_health` carries no company predicate at all, because
`FORCE ROW LEVEL SECURITY` applies to both sides — the `SELECT` can only see the open company's rows
and the `INSERT` can only write that company's. `CaseHealthRecomputeTest` asserts that with two
companies rather than trusting the comment. That is the single most reusable thing in the current
codebase for this work.

### 2.5 The background-job precedent already exists, and it is not `@Async`

`CaseHealthScheduler` is the shape any reporting worker must copy, and its header answers the
"how does a background job survive RLS and company context" question completely:

- A scheduled task starts with **no company at all** — `CompanyContext` is not `InheritableThreadLocal`
  and `CompanyContextTaskDecorator` clears it on every task, so a job that forgets fails closed.
- `company` is one of the few tables **not** under RLS, precisely so it can be read before any
  context exists. That is what makes a company loop possible.
- **One transaction per company, not one per run** — a single transaction spanning the loop would
  have to change `app.current_company` inside itself, which is the one thing
  `CompanyAwareTransactionManager` exists to prevent.
- Catch per company; one company's lock timeout must not cost the other forty-nine.

### 2.6 `AggregationPolicy` is shipped — in the wrong module for reuse

`com.tcms.execution.AggregationPolicy` is public and carries all five of §6e's values (`LATEST`,
`LATEST_PER_CONFIG`, `WORST`, `BEST`, `ALL`) plus `DEFAULT = LATEST`. `PlanStatisticsService` resolves
it over live `test_execution` rows and that resolution carries three fixes §46 paid for: the
phantom-not-run double count, `WORST` letting an unrecorded row outrank a recorded pass, and
`byConfiguration` under `LATEST` collapsing an entire environment out of the table.

`reporting` may not import `execution`. See §3, decision D — this is the plan's sharpest trade-off.

### 2.7 `report:view` and `report:export` are already seeded, and this is their first consumer

`V3` seeds both keys and grants them to **five of the six built-in roles** — Instance Admin, Company
Admin, Test Lead, Test Engineer and **Viewer** — withholding them only from Automation Service, with
the reason in the migration: *"a token that can read every report is a data-exfiltration path with no
operational benefit."* Neither key has ever been asked for in Java (`grep 'report:view'` over
`src/main` returns nothing).

So this slice family is the **eighth** instance of the pattern the handoff calls reliable enough to be
a search (`case:approve` §62, `library:manage` §64, `company:vocabulary` §69, `company:teams` §71,
`run:close` §72, the plan keys §73, the review keys §76, `case:comment` §79). **No new permission key
is invented anywhere in this plan** — the rule applied seven times (§67 `evidence:read`, §79
`suite:comment`, §80 assignment, §82 the override, §83, §84, §85) is that a key `V3` seeds to nobody
is a 403 no administrator can grant their way out of.

> **The finding that comes with it, and it is bad news for the gate mutations.** The only role
> withheld `report:view` is **Automation Service**, and there is **no API-token authentication in the
> product** — `com.tcms.auth` has twelve files and not one names `api_token`; token auth is M3. So
> **no persona any endpoint test can build lacks `report:view` or `report:export`**, and a mutation
> swapping either gate for the other, or deleting it, **reddens nothing**. This is §71's
> `company:teams` / `company:members` coincidence in a worse form, because there at least both
> candidate keys existed on human roles.
>
> The honest answer, and the one this plan requires of every gated slice: `role` is an
> **instance-level table with no `company_id` and a global unique name**, so an endpoint test may
> insert a custom `PROJECT`-scope role holding `case:read` and `project:read` and *not* the report
> keys, and grant it to a persona. That makes the gate discriminate and the mutation meaningful. It
> is the first custom role in the test suite; the ERD's exception-list note *"there are no custom
> roles in v1"* is about the product, not the fixture, and this plan does not change the product.

### 2.8 The contract has two dead endpoints and is missing two more

`docs/specs/openapi.yaml` declares, under the `reporting` tag:

- `GET /projects/{projectId}/dashboard` → **implemented** (§47).
- `GET /projects/{projectId}/reports` → array of `ReportDefinition`. **No server.** There is no
  `POST`, so the contract can list saved definitions and cannot create one.
- `POST /projects/{projectId}/reports/generate` → `202` + `ReportJob`. **No server.**

`ReportJob` is `{ jobId, status ∈ {PENDING,RUNNING,COMPLETED,FAILED}, format, downloadUrl }` with
`downloadUrl` **required and nullable**, and a comment explaining that a poller *"reads `status` to
decide whether to keep polling."*

**There is nothing to poll and nothing to download.** No `GET …/reports/jobs/{jobId}` and no artifact
content route exist anywhere in the spec. This is §67's finding verbatim — *"the download route is
not optional: `Evidence.url` is a REQUIRED contract field that had no server, so attach alone would
have had to invent it"* — and it means the generate slice must land three operations, not one.

**And there is no `report_job` table.** Not in `V1`, not in the ERD (§8 lists `report_definition` and
`report_artifact` and stops). `report_artifact.storage_key` is `NOT NULL`, so an artifact row cannot
exist before its bytes do and cannot serve as the job record. **The async contract has no home in the
schema, and that is the one genuine migration this plan needs.**

### 2.9 The mock has shipped a stub that violates the contract, and nothing calls it

`frontend/src/mocks/handlers/reporting.ts` answers `POST …/reports/generate` with

```ts
{ id: newId(), status: 'QUEUED', format: 'PDF', requestedAt: …, downloadUrl: null }
```

— `id` where the contract says `jobId`, `requestedAt` which the contract does not declare, and
`status: 'QUEUED'` which is **not one of the four enum values**. `GET …/reports` answers `[]`
unconditionally. No frontend hook calls either (`grep report` over `src/api/queries/` returns
nothing).

It is §52's *"the mock agrees with an idea of the feature"* class in its cheapest form — cheap only
because it has no consumer. §81 found the same class after it had been wrong for 28 slices. Fixing
these two handlers is part of the first slice that touches the contract, not a later tidy-up.

### 2.10 Storage: the port exists, in the module that may not share it

`execution.EvidenceStore` (four methods over an opaque key) + `FilesystemEvidenceStore` +
`tcms.storage.evidence.root`, from §67. Open question #28 is **resolved**: a storage port with a
filesystem adapter now, S3/MinIO later, and the cost accepted — *"a filesystem adapter has no signed
URL, so uploads proxy through the API."* Question #6 (2026-08-02) makes the S3 adapter a prerequisite
of the Helm chart and is *"the first thing in the plan that gives the deferred S3 adapter a
deadline"* — but the chart is not in M2.5 and neither is the adapter.

`reporting` may not import `execution`, so `EvidenceStore` cannot be reused as a type. See §3,
decision C.

### 2.11 There has never been a domain event

`CompanyScopedEvent` has **zero implementations**. Its javadoc's example handler is illustrative; the
grep for `implements CompanyScopedEvent` over `src/main` and `src/test` returns nothing but the
interface, `CompanyContext.openFor`, and two ArchUnit rules waiting for a first customer. §76
explicitly refused to create the product's first one for the review record.

This is the central cost input to decision A.

## 3. The hard decisions

Stated as decisions with the failure mode each prevents, per this repo's convention.

### Decision A — `ExecutionFact` is a real table, written by an idempotent recompute, **not** by events (yet)

**The choice.** `execution_fact` is populated by a single
`INSERT … SELECT … ON CONFLICT (execution_id) DO UPDATE` per company, in a `reporting` service shaped
exactly like `CaseHealthRecomputeService`, driven by a company-loop scheduler and **also invoked
synchronously at the head of every report job**. Domain events are named as the later optimisation
and are not built.

**Rejected: a view.** §6e is unambiguous — *"reporting built on live joins cannot be converted to a
read model incrementally"*, repeated in the plan's own list of things that must not be deferred, and
in `V1`'s comment on the table (*"Do NOT defer this"*). A view also cannot carry
`feature_ids UUID[]` cheaply, cannot be GIN-indexed, and would make §6e's partition-by-month escape
hatch unreachable. And it would make the module boundary a fiction: a view is invisible to ArchUnit,
so `reporting` would be reading `test_execution` with no seam file and nothing to stop the second,
third and fourth query.

**Rejected: events-only.** It is what §6e and the ERD both describe (*"event-updated tables,
maintained off Modulith domain events"*), and it is wrong to do **first**, for a reason the codebase
can name precisely: with zero `CompanyScopedEvent` implementations, no outbox consumer
(`outbox` is a `V1` table with no code), and `@Async` handlers whose failures have, in
`CompanyScopedEvent`'s own words, *"nowhere to report"* — an event-only fact log has **no rebuild
path**. A handler that throws, a restart mid-dispatch, or a result recorded before the handler was
deployed all produce a fact log that is permanently and silently short, and every report computed
from it is wrong in a way that looks exactly like a correct report. This repo has now paid for that
shape four times (§47's empty "Needs attention" panel, §53's silent card, §72's every-run-not-started,
§81's mock that had shipped a feature wrong for 28 slices) and the common thread is that a *claim
with no evidence behind it renders identically to a true one*.

An idempotent statement keyed on the PK **is** the rebuild path. It is also, verbatim,
`CaseHealthRecomputeService`'s own argument for itself: *"this service is deliberately the shape an
event handler would call — one public method, company taken from context, clock injected — so that
landing `ResultRecorded` later adds a handler and changes nothing here."*

**The cost, stated rather than discovered.** Three `execution_fact` columns are *frozen dimensions*
that a re-running projection would silently rewrite: `automation_status` (the case's, which moves),
`test_type_id`/`test_level_id`/`feature_ids` (the case's classification, which moves). A recompute
that `DO UPDATE`s them would retroactively re-file last quarter's results under this quarter's
taxonomy — the aggregate report's "failures by feature" section would change its own history every
hour. **So the `ON CONFLICT DO UPDATE` names only the result columns** (`status_kind`,
`counts_as_pass`, `executed_at`, `executed_by`, `duration_ms`, `release_*`, so an amended result is
corrected) **and deliberately omits the dimension columns**, which are therefore written once on
insert and never again. This is `ExecutionFacts`' *"the row is shared, the columns are not"* rule
reused rather than re-derived, and it is the slice's most important line.

**The second cost.** A report is only as fresh as the last refresh. Answered by refreshing the open
company's facts **inside the report job, before computing**, so a generated report's watermark is
exact; the schedule is only the floor for anything reading facts outside a job.

### Decision B — the async job is a table plus a company-loop worker, not `@Async`

**The choice.** `V27` creates **`report_job`**. `POST …/reports/generate` writes a `PENDING` row
inside the request's own transaction — where company context is already established from the session,
as it is for every write in the product — and returns `202` immediately. A `@Scheduled` worker
enumerates companies from the un-RLS'd `company` table, opens each context in turn, and claims that
company's oldest `PENDING` job. `CaseHealthScheduler`'s loop, one transaction per company, catch per
company.

**Why not `@Async` + `@TransactionalEventListener(AFTER_COMMIT)` on the request thread.** It is the
shape `CompanyScopedEvent`'s javadoc illustrates and it gives lower latency, and it fails the one
thing a job **record** exists for: an in-JVM dispatch is lost on restart, and the row sits `PENDING`
for ever with nobody to retry it and no symptom but a spinner. The whole reason §6e specifies a job
id rather than a long request is that the work outlives the request; making the work die with the
process gives back exactly what was bought.

**How it survives RLS — this is the part that is easy to get wrong and silent when wrong.**
`report_job` is company-owned and therefore RLS-protected, so a worker with no company context sees
**zero** rows (`V4`'s `nullif`, fail-closed) — a "find all pending jobs across the instance" query
returns nothing and the worker logs a successful tick having done nothing. That failure is invisible.
The company loop is not an optimisation, it is **the only way the worker can see any job at all**,
and it works for one specific reason `CaseHealthScheduler` writes down: `company` is deliberately not
under RLS so it can be read before any context exists.

**v1 concurrency: one job at a time, single-threaded, no `SKIP LOCKED`.** The filesystem storage
adapter already pins the deployment to one replica (open question #6), so a second worker has no
deployment to run in. `attempts` and `error` columns land now; a retry policy is named and not built
— a `FAILED` job is re-requested by the user, which is honest and costs one click.

### Decision C — output bytes go through a **second** storage port, and the download route ships with the first format

**The choice.** `reporting.ReportStore` (a port with `EvidenceStore`'s four methods) +
`FilesystemReportStore` + `tcms.storage.reports.root`, and
`GET /projects/{projectId}/reports/artifacts/{artifactId}/content` proxying the bytes, in the same
slice as the first format.

**This is not a blocker.** The absence of an S3 adapter is not what would stop reporting: open
question #28 is resolved, the filesystem adapter is the shipped answer for evidence today, and a
report file is smaller and rarer than a screenshot. What #6 blocks is the **Helm chart**, which is
not in M2.5. The plan should not, and does not, wait on object storage.

**What is a real blocker is PDF** — see §8.

**Why a second port and not a shared one.** `reporting` may not import `execution`, so
`EvidenceStore` is unreachable as a type. Two ports with four identical signatures is §58's E1 — the
copy that drifts — and it is accepted here **with the debt named in both headers**, because the
alternative is creating the `shared` module (decision E). The day either port grows a fifth method,
the other is where to look.

**Why the download route is not optional.** §67 settled this: `ReportJob.downloadUrl` is a *required*
contract field, so a generate endpoint shipped alone would have to invent a URL, and every client
would take the invention for the contract.

### Decision D — the aggregation policy is in the **first** computing slice, and the enum is duplicated while the algorithm is not

**Deferring it is refused.** §6e's whole argument is that *"getting this wrong is how reports lie"*
and that the chosen policy and full selection are **printed in the report header**. A first report
that quietly means `LATEST` has a default nobody chose, and the day the parameter arrives every
previously-generated PDF becomes uninterpretable. The enum already exists, is already public, and is
already a user-visible query parameter on plan statistics — the report that omits it would be the
*only* surface in the product that aggregates without saying how.

**The enum is duplicated into `reporting`**, with the duplication recorded in the file header and the
running count updated (`work.UserRefView` currently records `ApiProblem` ×2, `UserRefView` ×3; this
makes a fourth family). Cheaper than a module for one enum, and consistent with how this codebase has
already handled three forced wire-shape copies.

**The algorithm is NOT duplicated, and this is the load-bearing half.**
`PlanStatisticsService.resolve` is ~80 lines carrying three fixes §46 paid for in defects, and a
second Java copy of it is E1 at its most expensive. `reporting` resolves the policy **in SQL over
`execution_fact`** — a different implementation, over different data, answering the same question.
Two implementations of one rule is exactly what this codebase deletes on sight, so it is only
tolerable with the guard that makes them agree:

> **The cross-check test is part of the aggregate-report slice, not optional.** For a selection of a
> single plan, the report's per-status counts under each policy must equal
> `GET /plans/{planId}/statistics`'s under the same policy, asserted **against each other** rather
> than against literals — §32's and §46's shape, for §46's stated reason: *a literal agreeing with a
> wrong implementation is how both screens end up wrong together.* The defect it prevents is a plan
> page reading 94% and the release report reading 91%, for the same plan, on the same day, with no
> way to tell which is lying.

**One asymmetry must be written into both headers**: `PlanStatisticsService` sees *unrecorded*
executions (a fresh run's `UNTESTED` rows) and `execution_fact` structurally cannot (§2.3). So the
two agree on **recorded** results and the report's denominator is the plan's scope, obtained
separately. Discovering that inside the cross-check test rather than before it would read as a defect
in the new code.

### Decision E — no `shared` module in this plan

Tempting three times over (the two storage ports, `AggregationPolicy`, `UserRefView` ×4). Refused for
§76's reason about a `review` module: a new module needs plan §3 amended, `ModuleStructureTest`
edited, and an `allowedDependencies` decision — *"a fourth foundation module is a decision, not an
import"* — and this plan already spends one of those on `reporting`. Two module-list edits in one
milestone, one of them for an enum and two interfaces, is the wrong ratio. Named as the natural home
for all four the day a fifth arrives.

### Decision F — the on-screen report view reads a **stored** `JSON` artifact, not a second code path

§6e: *"The on-screen report view consumes the same model via JSON, so what you see is what exports."*
`report_artifact.format`'s `CHECK` is `('PDF','MD','HTML','CSV','XLSX')` — no `JSON`. So `V27` widens
that constraint and every job persists its `ReportModel` as a `JSON` artifact **in addition to** the
requested format.

The alternative — a synchronous `preview` endpoint that recomputes the model for the screen — is a
second code path producing a second answer, which is the precise drift §6e's one-model architecture
exists to prevent, and it would reintroduce the long request the 202 contract removed. Storing it
also makes determinism (§6e's last bullet) free: the exported HTML and the screen are provably the
same bytes rendered twice.

### R1 — the `reporting` module, and `execution_fact` gets a writer

**Builds.** `com.tcms.reporting` with `package-info.java`
(`allowedDependencies = {"tenancy", "project", "identity"}`, matching `repository`/`execution`/`work`)
· `ExecutionSource` — the module's single cross-module seam file, holding one
`INSERT … SELECT … ON CONFLICT (execution_id) DO UPDATE` · `ExecutionFactRefreshService`
(`@Transactional`, `CompanyContext.require()`) · `ExecutionFactScheduler` (company loop,
`@ConditionalOnProperty`) · `ExecutionFactProperties`. Amends `ModuleStructureTest`'s hard-coded list
(9 → 10) **and its rationale text**, which currently says `reporting` is one of the two still to
land.

**Module, and why not another.** `reporting`, and it has to be created to say so. The query names
`test_execution`/`test_run` (`execution`), `test_case`/`suite`/`case_classification` (`repository`)
and `case_status` (`execution`'s vocabulary, `repository`'s neighbour) — **three modules, and no
existing module may write it**, which is §81's argument arriving at a module that does not exist yet.
Putting it in `repository` (which already has `ExecutionFacts`) would make that file the second place
`repository` writes another module's read model and would give the dashboard's module ownership of
the release report's data. Putting it in `execution` makes `execution` read `suite`, which ArchUnit
refuses.

**Migration.** None — `execution_fact` and its five indexes are `V1`. **`V27` stays free.** Policy
count stays **58**.

**Contract.** No change. No endpoint.

**Permission.** None — nothing is exposed.

**Defect prevented.** A read model with no rebuild path (decision A), and the dimension-freeze defect:
without the split `ON CONFLICT` set-list, an hourly job silently re-files historical results under the
current taxonomy, so last quarter's "failures by feature" chart changes every hour and nobody can
name when.

**Notes.** This is the one slice with no user-visible output, and it is the exception that has to be
argued: it is justified because R2 makes it visible one slice later and because every other slice in
this plan reads the table it fills. If its own test set feels thin, land R1 and R2 as one commit pair
rather than padding R1.

### R2 — `failing_repeatedly`: the first health signal derived from the fact log

**Builds.** One statement in `ExecutionSource` deriving `case_health.failing_repeatedly` from
`execution_fact` (the last N executions per case, N from properties beside
`CaseHealthProperties.longUnexecuted`), wired into the same scheduler tick. Signal 3 of 9 becomes
real.

**Module, and why that one.** `reporting` writes it, `repository` keeps writing its own two, and
**that is exactly the design `ExecutionFacts`' header already prescribes**: *"a signal's owner writes
its own column and no others; the row is shared, the columns are not."* This is the first time a
second module exercises that rule, which is the slice's real content.

**Migration.** None. `V27` stays free. **Contract.** None — `HealthSignal.FAILING_REPEATEDLY` is
already in the enum, already in `healthLabels`, already renderable by the dashboard tile and the
board's `CASE_MAINTENANCE` card. **Permission.** None new.

**Defect prevented.** Two: an `ON CONFLICT` that clobbers `repository`'s columns (the mutation §53
already ran once, now newly reachable from a second writer), and the §47/§53 empty-panel class — a
signal named in the enum, labelled in the UI and asserted by nothing, which reads as *"nothing is
failing repeatedly"* on every deployment.

**Finding to record while here.** `case_health` has **ten** boolean columns and `HealthSignal` has
**nine** members — `incomplete` has no enum member and therefore no reader. Found, not fixed; it

### R3 — `V27`: the job record, the store, and the pipeline end to end with one report and two formats

The biggest slice in the plan, and it is the one that cannot be subdivided without shipping a 202
nobody can poll.

**Builds.** `V27__report_job.sql` — the `report_job` table
(`id`, `company_id NOT NULL`, `project_id NOT NULL`, `definition_id NULL`, `type`, `format`,
`parameters JSONB`, `status CHECK IN ('PENDING','RUNNING','COMPLETED','FAILED')`, `artifact_id NULL`,
`model_artifact_id NULL`, `error`, `requested_by`, `requested_at`, `started_at`, `finished_at`,
`attempts`), its RLS policy, an index on `(company_id, status, requested_at)` for the claim query,
**and the `report_artifact.format` CHECK widened to include `'JSON'`** (decision F) ·
`ReportJob`/`ReportArtifact`/`ReportDefinition` entities + repositories · `ReportStore` port +
`FilesystemReportStore` · `ReportModel` (the serializable value: title, metadata, sections, tables,
chart series) · `MarkdownReportRenderer` + the JSON writer · `RunSummaryReport` (the first type) ·
`ReportJobService` (request) + `ReportJobRunner` + `ReportJobScheduler` (company loop) ·
`ReportController`.

**Endpoints.** `POST /projects/{projectId}/reports/generate` (implements the declared one) ·
**`GET /projects/{projectId}/reports/jobs/{jobId}`** (new) ·
**`GET /projects/{projectId}/reports/artifacts/{artifactId}/content`** (new).

**Module.** `reporting`. The report reads `execution_fact` only, which is why R1 comes first.

**Migration.** **`V27`** — the only one in this plan. Two things the cache flags explicitly and both
apply: the policy must be written with **`V4`'s `nullif(current_setting('app.current_company', true), '')::uuid`
predicate and not `V1`'s bare one** (a table born with the old spelling reintroduces the reset-GUC
500 on exactly that table), and `SchemaConventionTest`'s policy count moves **58 → 59** — the count is
what makes the predicate check non-vacuous, so moving it is the point. No `GRANT` needed;
`deploy/postgres/initdb/10-tcms-roles.sql` sets `ALTER DEFAULT PRIVILEGES` before Flyway runs.

**Contract.** **Changes.** Two new operations; `ReportJob` gains nothing (its four fields are already
right); `generate`'s request body gains `parameters` typing per report type. `npm run gen:api` must
run and `frontend/src/mocks/handlers/reporting.ts` must be corrected to the contract in this slice —
it currently answers `id`/`requestedAt`/`QUEUED`, none of which the contract declares (§2.9).

**Permission.** `report:export` on generate and on artifact download; `report:view` on the job poll.
**Both derived, neither new** — `V3` has seeded them since M0 and this is their first consumer
(§2.7). Read the gate-mutation warning in §2.7 before writing the tests: without a custom-role
persona these gates cannot be shown to do anything.

**First format is `MD` + `JSON`, deliberately, and `HTML` is R4.** Markdown needs no template engine,
no CSS inlining and no browser, so R3 proves the *pipeline* — job, worker, context, store, download —
rather than a renderer. **`PDF` must be refused with a `400` at request time**, naming that PDF
rendering is not installed, never accepted into a job that fails an hour later: the contract's
`format` enum already offers it and a client cannot tell an unsupported format from a broken server
by watching a job go `FAILED`.

**Defect prevented.** Four, each already named by something in the repo: a 202 returning a job id
with nothing to poll and a required `downloadUrl` with no server (§67); a worker that queries
globally, sees zero rows under RLS and logs a successful tick having done nothing (decision B); an
artifact row written before its bytes (§67's rows-then-bytes ordering, which inverts here — a report
must write **bytes first, row second**, because the row is what makes the artifact *reachable*, and
the tolerable inconsistency is a blob no row names rather than a `COMPLETED` job whose download
404s); and a `format: PDF` accepted into a queue that cannot serve it.

> The ordering inversion versus `EvidenceService` is deliberate and must be argued in the code, not
> assumed — §67 chose rows-first because a missing blob is findable by an operator and an orphan blob
> is not. Here the job row already names the work, so an orphan blob **is** findable (it is the
> job's), and the failure that matters is a job reporting success with nothing behind the link.

### R4 — the HTML renderer, and the report header §6e makes mandatory

**Builds.** `HtmlReportRenderer` (Thymeleaf → **single self-contained file**, CSS inlined, images
base64) over the same `ReportModel`, plus the header block, which is where the design content is:
report title · report type · **the aggregation policy in words** · **the full selection/filter set** ·
generating user · generation timestamp · **the project scope actually covered** · company logo with
per-project override (§6u branding, defaulting to the company's).

**Module.** `reporting`. **Migration.** None; `V27` must still be the head. **Contract.** No change —
`format` already enumerates `HTML`. **Permission.** None new.

**Defect prevented.** Two distinct ones. First, §6e's: *"two teams reading '94% pass' can mean
entirely different things"*, which is why the policy is printed rather than recorded in metadata.
Second, and sharper because it is invisible: plan §390 — *"cross-project reports are scoped to granted
projects, so an aggregate report run by a regular user silently covers less than the same report run
by a Company Admin. The report header must state the scope it actually covered, or two people will
compare incomparable numbers."* §83 and §84 have now made exactly this bound the design of two boards
(*"two people asking for the same team's board receive different boards, and that is the design"*);
a report is the same bound with the answer printed on paper and forwarded to a client, which makes
stating it non-negotiable.

**Also here:** the self-contained requirement is testable and should be tested — the generated HTML
must contain no `http(s)://` asset reference. §6e's own words: *"a self-contained file that needs a
CDN to draw its diagrams is not self-contained."*

## 5. Recommended first slice: **R1**

Three reasons, in order of weight.

**It is the only slice whose design decision constrains every other one.** Whether `execution_fact`
is fed by an idempotent recompute or by domain events determines the freshness story, the report
job's first step, whether the product acquires its first `CompanyScopedEvent`, and whether a
mis-delivered fact is repairable at all. Deciding that inside R3, where a job pipeline is already
competing for attention, is how it gets decided by whichever option was easier to type.

**It is where the cheap discoveries are, and they are load-bearing.** This pass verified on paper that
every `execution_fact` column has a source; R1 is where that stops being paper. If `feature_ids`
cannot be assembled without an unacceptable join, or if `suite_path` needs a `@ColumnTransformer`
(the `ltree` trap `Suite.path`'s javadoc names by name and §69 hit anyway), or if `configuration_id`
turns out reachable only through a run that has been soft-deleted — every one of those changes the
*selection dimensions* of the aggregate report. Finding it in R6 invalidates three slices.

**Nothing else can start.** There is no `reporting` package, so no other slice in this plan has
anywhere to put a file, and the alternative — starting with R3's job pipeline and having it read
`test_execution` directly "for now" — creates the second cross-module query that §2.4's whole seam
convention exists to prevent, in the module's first week.

The honest cost, stated: R1 ships nothing a user can see, which this repo normally refuses. R2 is one
statement long and lights up a dashboard tile and a board card that have been structurally empty
since §47, so the pair is the smallest honest unit if a slice with no screen is unacceptable.

## 6. Cross-cutting rules every slice in this plan inherits

- **`company_id NOT NULL` on `report_job`**, leading its composite index. `SchemaConventionTest`
  fails the build otherwise, and the ERD §0.1 exception list is closed to additions without a
  decision.
- **Every repository interface carries `@Transactional(readOnly = true)`** or its derived and
  `@Query` methods run with no company context and return zero rows, fail-closed and silent.
  `RepositoryTransactionTest` derives the list from the live context.
- **Company context is opened *around* the transaction, never inside it** —
  `CompanyAwareTransactionManager` hooks `doBegin`. `CompanyProvisioningService.provision():154-161`
  is the canonical ordering and the scheduler loop is the second one.
- **No `Instant.now()`** — `ArchitectureRulesTest.nothingCallsNowDirectly` fails the build; take the
  `Clock` bean, which is truncated to microseconds.
- **`-Werror`**, and `./gradlew build` locally is the only thing that runs the 1500+ tests — CI runs
  `-x test`.
- **Fixture UUID prefixes and company slugs are hand-managed and have collided five times** (§19 …
  §62). Each new test class takes its own namespace; `re-`, `rj-`, `rf-` are unclaimed today but
  must be re-checked at write time.
- **Browser passes and backend mutation checks are deferred and batched (§65).** Every slice appends
  its rows to `docs/verification/frontend-browser-checks.md` and
  `docs/verification/backend-mutation-checks.md` and **runs none of them**. A slice in an unrun queue
  is *built and unverified* and must be described that way.
- **`openapi.yaml` is the contract**: change it, `npm run gen:api`, adapt both sides in one commit,
  and **add the `required` array to every new schema including inline nested objects** —
  `ContractConventionTest` and `requiredPropertiesHaveAComponent` both check it, and §80's slip was
  caught by exactly that.

## 7. Open questions this plan cannot answer

Each is a `[TBD]` with a named owner, not an assumption buried in a table.

1. **`[TBD — user]` Report retention.** `report_artifact` has no `expires_at` and §6n names storage
   growth as the risk. A cycle report per release, kept for ever, on one disk. Options: never delete
   (v1, honest, and the disk is backup-critical per #28), delete after N days, or delete only
   unpinned artifacts (an artifact pinned as a `GENERATED_REPORT` in the register — §6n — must
   survive). **Blocks nothing until R3 ships bytes; must be answered before a real deployment.**
2. **`[TBD — user]` Per-project storage quota.** Open question #28 left it open and named the
   filesystem adapter as making it *more* pressing. Reports add a second writer to the same disk.
3. **`[TBD — data-architect]` Does `execution_fact` need `plan_id` to be multi-valued?** A run
   belongs to at most one plan, so the column is fine today; a case executed in a run outside any
   plan carries `NULL` and is therefore invisible to any plan-keyed selection. Confirm that is
   intended before R6 builds selection on it.
4. **`[TBD — user]` What is the report's own scope bound?** §390 says a report covers only granted
   projects. `ProjectService.readAllVisible` (§83) is the shipped answer for a cross-project read,
   but §6e's aggregate report is declared *per project* by its path. Cross-project reporting is
   therefore **not in this plan** and needs the same decision §83/§84 made for the boards — which of
   the reader's and the subject's bounds wins — before it is.
5. **`[TBD — qa]` Can the report gate be made to discriminate at all** without a custom test role
   (§2.7)? If the answer is no, `SeedDataTest` should carry a computed check recording the
   coincidence, the way §71's `teamManagementAndMemberManagementAreStillHeldTogether` does — *"when
   that check FAILS it is the good case."*

## 8. What this plan does **not** cover — named, not silently dropped

- **PDF rendering.** Decided (open question #11, resolved 2026-08-02: headless Chromium, ~300MB image
  cost accepted) and **not built**: there is no Chromium or Playwright in the image, no process pool,
  no test lane, and no answer for what a self-hoster with a tight image gets. It is its own
  infrastructure slice with a devops half, and R3 refuses `format: PDF` with a `400` until it lands.
  §6e's own note that the container should run it *"as a sidecar-capable component so self-hosters
  with tight images can disable PDF"* is an unmade deployment decision, not just a dependency.
- **S3 / MinIO object storage.** Resolved as deferred (#28); a prerequisite of the Helm chart (#6),
  not of reporting. `FilesystemReportStore` is the shipped answer and the deployment stays
  single-replica, which it already is.
- **Scheduled reports.** §6e phase 2. `report_definition.schedule_cron` stays unmapped; there is no
  notification channel — all four of §6g's events have a trigger and no channel, per the cache.
- **Notifications and email/Slack delivery.** Same absence, one layer down. `outbox` is a `V1` table
  with no code.
- **Doc-structured reports and Mermaid.** §6i's half. Blocked on `doc_link` having a writer, which it
  does not (§2.1), and on a `DocBlockType` Mermaid member, which does not exist.
- **Coverage matrix report.** Same blocker — it is *defined* as a query over `doc_link`.
- **Evidence-bundle export.** Needs to read `evidence` and `attachment` rows, which live in
  `execution` and are unreachable from `reporting` except through the seam; and it needs
  `EvidenceStore`, which is `execution`'s port. It is a real slice, and it is the strongest argument
  for the `shared` module decision E defers.
- **Release comparison, trend, flakiness.** §6e's phase-3 column. `execution_fact` is what makes them
  cheap later, which is R1's justification and not R1's scope.
- **`suite_run_summary` and `plan_snapshot` writers.** §6p's rollups, still absent — §46 deliberately
  computes plan statistics on read instead, *"with the argument `RunService` already makes: a figure
  recomputed per request cannot go stale relative to a result recorded a second ago."* Nothing in
  this plan needs them, and building them would create a third answer to "how did this plan do".
- **CSV / XLSX.** In the `report_artifact` CHECK and in §6e's diagram; no consumer asks for them.
- **The remaining six `case_health` signals** (`outdated_spec_changed`, `stale_approval`,
  `condition_drift`, `stale_automation`, `unlinked`, `orphaned`) and the unnamed `incomplete` column.
  Each needs a source that does not exist yet — approvals need a stale-approval definition, the two
  link signals need `doc_link`, `stale_automation` needs M3 ingestion.
- **Cross-project reporting.** Open question 4 above.
- **The audit verb `report.exported`.** The ERD names it as an example `audit_event.action`. Writing
  it is one line in R3 and should be done — but note the live trap the cache records:
  `audit_event.target_type` is spelled two ways across the codebase and **nothing reads the column
  yet** (`audit:view` and `project:audit` both have zero consumers), so a new writer must use the
  snake_case table name (`report_job`) and not invent a third spelling.
