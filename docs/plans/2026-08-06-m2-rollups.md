# M2 rollups — `suite_run_summary` and `plan_snapshot` get writers, and two screens stop scanning

**Date:** 2026-08-06 · **Written by:** `ep-writing-plans`

> **For agentic workers:** REQUIRED SUB-SKILL: use `ep-executing-plans` (inline, the default) to
> implement this plan phase-by-phase. Steps use checkbox (`- [ ]`) syntax. Backend work additionally
> loads `be-java:be-java`, `be-java:be-java-database-code` and `data:data-migrations` per
> `CLAUDE.md`. **Commit at the end of each phase, after that phase's gate passes.**

**Goal:** Give `suite_run_summary` and `plan_snapshot` — two `V1` tables that have been discussed in
javadoc and written by nothing for the whole life of the project — a writer, and make the two screens
§6p designed them for read them instead of scanning `test_execution` per request.

**Architecture:** An idempotent recompute in `reporting`, driven by the existing per-company
scheduler tick, exactly as `ExecutionFactRefreshService` already does for `execution_fact` (§86).
`execution` then reads the two rollups back through **one** new seam class, the shape
`work.BoardFacts` established for a module reading two foreign modules. No events, no outbox, no
incremental write path — the statement keyed on the primary key *is* the rebuild path.

**Tech Stack:** Java 21 · Spring Boot 3.5.6 · Spring Modulith · native SQL through `EntityManager` ·
Flyway (`V34` is the next free number) · Testcontainers Postgres 17 · Vite/React/MUI/TanStack Query
on the client.

---

## 0. Why this slice exists, and what it is not

Round 3 of the remaining-scope assessment (`docs/audits/2026-08-05-remaining-scope-assessment.md`
§1.1) moved M2 **backwards, 90% → 85%**, because its rollup deliverable turned out to have no code
at all — invisible to round 2's check because both tables are *discussed* in comments. Nothing was
un-built; the earlier figure was wrong. This slice is what closes that.

It is **not** a performance emergency. `PlanStatisticsService`'s own header already states the
position plainly and it is correct: a figure recomputed per request cannot be stale against a result
recorded a second ago, the work is bounded by (cases in scope × runs of the plan), and it is "a few
thousand rows for a plan anyone would recognise". What it also says is where that stops being true —
"a nightly suite of 500 cases over a year" — and what to do about it:

> *"the migration path is to feed the rollup and read it here, with this class as the definition of
> what the rollup must produce."*

**That sentence is this plan's specification.** The existing service is the oracle: every number the
rollup path produces must equal the number the live path produces today, and the tests are written
that way round rather than as fresh assertions about the rollup.

## 1. The seven decisions, and the two that are the finding

Each is settled here so it is not re-litigated in a phase. Where a decision reverses or narrows
something already written down, the older text is struck through in the code rather than deleted.

### D1 — Idempotent recompute, not an event handler

§6p says both rollups are "updated incrementally as results land". That is the right steady state and
the wrong thing to build first, for **verbatim §86's reason**: the product has zero
`CompanyScopedEvent` implementations, no outbox consumer, and `@Async` handler failures have
"nowhere to report". An event-only rollup has **no rebuild path**, and a rollup that is silently
short renders identically to a correct one. A statement keyed on the primary key is the rebuild path;
landing `ResultRecorded` later adds a handler that calls the same service and changes nothing.

### D2 — Suite membership is the three-arm union, and the filed arm is §98's finding one screen on

`suite_run_summary` needs "which of this run's cases does suite S hold". The tempting predicate is
`c.suite_id = s.id` — one column, what the schema looks like it wants, and **against a suite defined
by a tag rule it resolves to nothing**: a summary of `0 of 0, 100%` over a run that covered forty of
that suite's cases. That is §98's count-versus-grid defect and §99's empty-checklist defect arriving
a third time, in a table.

So membership is `CaseFacts#memberOf`'s three arms — filed (`test_case.suite_id`) ∪ added
(`suite_case`) ∪ tag-matched (`suite_tag_rule` ⋈ `case_tag`) — written **once**, in `ExecutionSource`,
as the fourth copy of a predicate that ERD §0.2's module boundary forces to exist more than once.
`SuiteScopeAgreementTest` gets a third member.

### D3 — **`suite_run_summary` FREEZES its membership, and that is what `membership_snapshot` is for**

This is the first of the two findings.

A run's executions are fixed at create time (§42), so *which cases ran* cannot move. **Which suites
claim those cases moves every time somebody adds a tag.** A recompute that re-derives membership on
every tick therefore rewrites last March's pass rate: a case tagged `checkout` today appears in the
March run's Checkout summary, whose total silently goes 43 → 44 and whose percentage moves. Nobody
can name when it changed, and both numbers look equally correct.

§6p resolved this before the table had a writer — open question **#32, as-executed membership is the
default**: *"the run shows the cases the suite held when it ran; a later suite edit cannot
retroactively change a past run's coverage."* `membership_snapshot JSONB` is the column that exists
to hold that, and this is the slice that fills it.

It is also **§86's frozen-dimension argument reaching a second table**: a frozen dimension that
should have moved is one statement to change; a moving dimension that should have been frozen has
already destroyed the history it rewrote.

**Implementation consequence, and the reason it is two statements rather than one `ON CONFLICT`:**
counts must be tallied over the *frozen* membership, not over today's. A single upsert cannot do
that, because the row it would conflict with is the only place the frozen set is recorded. So:

1. `INSERT … ON CONFLICT DO NOTHING` — writes new `(run, suite, configuration)` rows with
   `membership_snapshot` and `suite_version_no` captured as-of now.
2. `UPDATE … FROM (tally over the row's own `membership_snapshot`)` — corrects the counts of rows
   that already exist, and structurally cannot touch the two frozen columns.

Making the freeze structural rather than a discipline about an `ON CONFLICT` set-list is deliberate:
§86's fifteen omitted columns are correct and are held only by a reviewer noticing.

### D4 — `suite_run_summary` is never pruned; `plan_snapshot` **must** be

The second finding, and it is the asymmetry between two tables that look like siblings.

- **`suite_run_summary` is history.** A row says "this is how suite S did in run R". A suite that
  stops claiming a case does not un-run it. Nothing is deleted, `deletedAt` on the run is a flag the
  reader renders (`runDeleted`, §6p, §49), and this matches `execution_fact`'s append-only rule.
- **`plan_snapshot` is current state** — `V1`'s own comment: *"The CURRENT latest result per case per
  configuration."* A case removed from the plan's scope, or soft-deleted, **must lose its row**, or
  the plan page argues readiness from a case the plan no longer covers. `PlanStatisticsService`
  already handles exactly this in Java (`rowsInScope` drops out-of-scope executions, and its header
  calls the mirror case "easier to miss"); moving the computation into a table moves that filter into
  a `DELETE`.

A recompute with no delete pass is the failure mode here, and it is silent: the plan's totals simply
stay too high for ever, with no row anywhere that looks wrong.

### D5 — `plan_snapshot` can serve exactly two of the five aggregation policies

`AggregationPolicy` has five members and the table holds *latest per (case, configuration)* only.

| Policy | Served from | Why |
|---|---|---|
| `LATEST_PER_CONFIG` | the rollup | that is literally the table's grain |
| `LATEST` | the rollup | latest-per-case is the row with `max(executed_at)` among a case's config rows |
| `WORST` · `BEST` · `ALL` | **the live path, unchanged** | each needs every execution; a latest-only table structurally cannot answer them |

This is not a shortfall to work around — it is what the table is. What matters is that **the same
screen must not answer from two sources with different staleness and no way to tell**, which is
§65's two-contradictory-percentages lesson with the contradiction hidden behind a dropdown. Hence D7.

### D6 — the trend line comes from `execution_fact`, not from a scan and not from `plan_snapshot`

`PlanStatisticsView.trend` is pass rate per run of the plan. `plan_snapshot` cannot hold it (it keeps
one row per case, not per run), and computing it live would mean the very
`TestExecutionRepository#findForPlan` scan the rollup exists to remove — so the rollup path would be
*slower* than today, having added a table and kept the scan.

`execution_fact` already carries `plan_id`, `run_id`, `status_kind`, `counts_as_pass` and
`executed_at`, and has `execution_fact_plan_idx ON (company_id, plan_id, executed_at DESC)`. A trend
is one `GROUP BY run_id` over it. All three tables are `reporting`'s, so the seam stays one class.

### D7 — freshness goes **on the wire**, because §6p says the stale plan page is the dangerous one

> §6p: *"A plan page showing 94% from three weeks ago, presented as current, is the most dangerous
> screen in the product."*

The response already carries `stale` (nothing executed in 14 days) — that is a statement about the
*executions*. This slice introduces a second, different staleness: the numbers can now be up to one
scheduler tick behind a result that was recorded a minute ago, which the live path could not be. A
client that cannot tell those apart will present one as the other.

So both responses gain **`computedAt: string | null`** — the rollup's own `updated_at`, and `null`
when the answer was computed live (the three policies of D5, and a plan with no rollup row yet).
`null` is a positive statement, not a missing value: *this number is as of this instant*.

### D8 — nothing is refreshed synchronously on the read path

Tempting, and it defeats the slice: a refresh per page load is the scan plus a write. §87 already
established the one place a synchronous refresh is right — a report job refreshes its own company
before computing, so the schedule never decides what a *generated report* says. A screen is not a
report, and `computedAt` is how a screen tells the truth about its own age instead.

```sql
-- V34 — the read indexes the two M2 rollups need, and V1 did not ship because the tables had no
-- reader to shape them for.
--
-- Both PRIMARY KEYs are the write path's: suite_run_summary is (run_id, suite_id, configuration_id)
-- and plan_snapshot is (plan_id, case_id, configuration_id). Neither serves the read, which arrives
-- with a suite or a plan and no run and no case.
--
-- company_id LEADS both, per ERD §0.1 point 3 and SchemaConventionTest#companyIdLeadsCompositeIndexes
-- — a trailing company_id costs storage and buys nothing, because the planner cannot seek on it.

CREATE INDEX suite_run_summary_suite_idx
    ON suite_run_summary (company_id, suite_id);

COMMENT ON INDEX suite_run_summary_suite_idx IS
    'The suite history page: every run of one suite. The PK leads with run_id and cannot serve it.';

CREATE INDEX plan_snapshot_plan_idx
    ON plan_snapshot (company_id, plan_id);

COMMENT ON INDEX plan_snapshot_plan_idx IS
    'The plan statistics page: every case of one plan. The PK leads with plan_id, so this is nearly '
    'redundant — it exists for the company_id seek, which the PK cannot do at all.';
```

- [ ] **Step 5: Add the two statements to `ExecutionSource`.**

Both go in `ExecutionSource` and **not** in a new class: its header states that a second class in
`reporting` naming `test_execution` ends the property the file exists for, "and it ends it for the
most tempting reason there is — that the new query is short."

```java
    /**
     * Insert one {@code suite_run_summary} row per {@code (run, suite, configuration)} the open
     * company has a recorded execution for, capturing the membership as it stands now.
     *
     * <h2>{@code ON CONFLICT DO NOTHING}, and the freeze is structural</h2>
     *
     * <p>An existing row's membership is <strong>never</strong> revisited — see
     * {@link #correctSuiteRunCounts()}, which tallies over the stored snapshot. §6p open question
     * #32 settled as-executed membership as the default, and a recompute that re-derives today's
     * membership moves a March run's total from 43 to 44 the day somebody adds a tag, with both
     * numbers looking equally correct and nobody able to name when it changed. That is §86's
     * frozen-dimension argument arriving at a second table, and it is spelled as two statements
     * rather than as an {@code ON CONFLICT} set-list because a set-list is held only by a reviewer
     * noticing which fifteen columns are absent.
     *
     * <h2>Three arms, not {@code c.suite_id = s.id}</h2>
     *
     * <p>The fourth copy of {@code CaseFacts#memberOf}'s union, and the module boundary is what
     * makes it a copy rather than a call ({@code ExecutionSource}'s header, ERD §0.2). One column
     * is what the schema looks like it wants and resolves to <strong>nothing</strong> for a
     * tag-defined suite — a summary of {@code 0 of 0, 100%} over a run that covered forty of that
     * suite's cases (§98, §99). {@code SuiteScopeAgreementTest} holds this copy to the others.
     *
     * <p>{@code suite_version_no} is the version in force <em>at the run</em> and is frozen with the
     * membership, never {@code suite.current_version_no}: today's number beside an old run puts
     * this year's composition under last year's pass rate.
     *
     * @return rows inserted. Zero on a steady-state tick is ordinary — every run already has its
     *         summary — which is why the correcting statement returns its own count separately.
     */
    int insertNewSuiteRunSummaries() {
        return entities.createNativeQuery("""
                INSERT INTO suite_run_summary (
                        company_id, run_id, suite_id, configuration_id, suite_version_no,
                        passed, failed, blocked, skipped, not_run, total,
                        membership_snapshot, updated_at)
                SELECT m.company_id, m.run_id, m.suite_id, m.configuration_id,
                       COALESCE((SELECT max(v.version_no) FROM suite_version v
                                  WHERE v.suite_id = m.suite_id
                                    AND v.created_at <= m.last_executed_at), 1),
                       m.passed, m.failed, m.blocked, m.skipped, m.not_run, m.total,
                       m.case_ids, now()
                  FROM (
                        SELECT e.company_id,
                               e.run_id,
                               s.id AS suite_id,
                               r.configuration_id,
                               count(*) FILTER (WHERE st.kind = 'PASSED')  AS passed,
                               count(*) FILTER (WHERE st.kind = 'FAILED')  AS failed,
                               count(*) FILTER (WHERE st.kind = 'BLOCKED') AS blocked,
                               count(*) FILTER (WHERE st.kind = 'SKIPPED') AS skipped,
                               count(*) FILTER (WHERE st.kind IN ('UNTESTED','RETEST','WIP')
                                                   OR st.kind IS NULL)     AS not_run,
                               count(*)                                    AS total,
                               max(e.executed_at)                          AS last_executed_at,
                               to_jsonb(array_agg(e.case_id ORDER BY e.case_id)) AS case_ids
                          FROM test_execution e
                          JOIN test_run  r ON r.id = e.run_id
                          JOIN test_case c ON c.id = e.case_id
                          JOIN suite     s ON s.project_id = e.project_id
                          LEFT JOIN case_status st ON st.id = e.status_id
                         WHERE ( c.suite_id = s.id
                                 OR EXISTS (SELECT 1 FROM suite_case sc
                                             WHERE sc.suite_id = s.id AND sc.case_id = c.id)
                                 OR EXISTS (SELECT 1 FROM suite_tag_rule tr
                                              JOIN case_tag ct ON ct.tag = tr.tag
                                                               AND ct.case_id = c.id
                                             WHERE tr.suite_id = s.id) )
                         GROUP BY e.company_id, e.run_id, s.id, r.configuration_id
                       ) m
                    ON CONFLICT (run_id, suite_id, configuration_id) DO NOTHING
                """).executeUpdate();
    }

    /**
     * Re-tally the counts of {@code suite_run_summary} rows that already exist, over
     * <strong>the membership each row froze</strong> and never over today's.
     *
     * <p>This is the half that follows an amended verdict: a result re-recorded from FAILED to
     * PASSED must move the row, and nothing else may. The {@code case_id IN (the row's own
     * snapshot)} predicate is what makes that true by construction — there is no set-list to get
     * wrong, and a case that joined the suite after the run is not in the snapshot and therefore
     * cannot be counted.
     *
     * <p>{@code not_run} counts the statuses that are not verdicts and the executions with no status
     * at all: creating a run writes one empty execution per case in scope (§42), and those are
     * exactly the "6 not run" §6p requires beside a pass percentage — <em>"a 100% pass rate over 3
     * of 47 cases is otherwise actively misleading."</em> This is the one place a rollup here differs
     * from {@code execution_fact}, which is recorded-only by construction and whose header says
     * coverage denominators can never come from it.
     *
     * @return rows corrected.
     */
    int correctSuiteRunCounts() {
        return entities.createNativeQuery("""
                UPDATE suite_run_summary srs
                   SET passed = t.passed, failed = t.failed, blocked = t.blocked,
                       skipped = t.skipped, not_run = t.not_run, total = t.total,
                       updated_at = now()
                  FROM (
                        SELECT s.run_id, s.suite_id, s.configuration_id,
                               count(*) FILTER (WHERE st.kind = 'PASSED')  AS passed,
                               count(*) FILTER (WHERE st.kind = 'FAILED')  AS failed,
                               count(*) FILTER (WHERE st.kind = 'BLOCKED') AS blocked,
                               count(*) FILTER (WHERE st.kind = 'SKIPPED') AS skipped,
                               count(*) FILTER (WHERE st.kind IN ('UNTESTED','RETEST','WIP')
                                                   OR st.kind IS NULL)     AS not_run,
                               count(*)                                    AS total
                          FROM suite_run_summary s
                          JOIN LATERAL jsonb_array_elements_text(s.membership_snapshot) AS mc(id)
                                    ON true
                          JOIN test_execution e ON e.run_id = s.run_id
                                               AND e.case_id = mc.id::uuid
                          LEFT JOIN case_status st ON st.id = e.status_id
                         GROUP BY s.run_id, s.suite_id, s.configuration_id
                       ) t
                 WHERE srs.run_id = t.run_id
                   AND srs.suite_id = t.suite_id
                   AND srs.configuration_id = t.configuration_id
                   AND (srs.passed, srs.failed, srs.blocked, srs.skipped, srs.not_run, srs.total)
                       IS DISTINCT FROM (t.passed, t.failed, t.blocked, t.skipped, t.not_run,
                                         t.total)
                """).executeUpdate();
    }
```

The trailing `IS DISTINCT FROM` is not an optimisation for its own sake: without it every tick
rewrites every row and bumps `updated_at`, so `computedAt` (D7) would advance on a page whose numbers
have not changed in a month — a freshness field that always says "just now" is a freshness field that
says nothing.

```java
 * inside it: that service's header argues its two statements share a transaction because one
 * <em>reads what the other writes</em>, which is not true of these. What is true of both is the
 * design — idempotent recompute keyed on the primary key, one transaction per company, repaired by
 * the next tick rather than lost.
 *
 * <p>Ordering within the tick is nonetheless load-bearing and is the scheduler's, not this class's:
 * the plan trend reads {@code execution_fact}, so the fact refresh runs first or the trend line is
 * a quarter-hour behind the headline it sits next to — which is invisible, because a stale sparkline
 * renders exactly like a fresh one.
 */
@Service
public class RollupRefreshService {

    private static final Logger log = LoggerFactory.getLogger(RollupRefreshService.class);

    private final ExecutionSource source;

    RollupRefreshService(ExecutionSource source) {
        this.source = source;
    }

    /**
     * @return how many rollup rows were written or corrected, across both tables.
     * @throws IllegalStateException via {@link CompanyContext#require()} if no company is open —
     *     loud, for {@link ExecutionFactRefreshService}'s stated reason: the alternative is a job
     *     that quietly writes nothing under {@code V4}'s {@code nullif} and logs a successful tick.
     */
    @Transactional
    public int refresh() {
        CompanyContext.require();

        int suitesInserted = source.insertNewSuiteRunSummaries();
        int suitesCorrected = source.correctSuiteRunCounts();
        int planRows = source.refreshPlanSnapshot();
        int planPruned = source.prunePlanSnapshot();

        log.debug("Rollups refreshed: suite +{} ~{}, plan ~{} -{}",
                suitesInserted, suitesCorrected, planRows, planPruned);
        return suitesInserted + suitesCorrected + planRows + planPruned;
    }
}
```
